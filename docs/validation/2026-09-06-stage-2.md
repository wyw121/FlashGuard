## 阶段 2 专项验证

Redis 官方 `linux/amd64` manifest 为 `sha256:3a7a8bb1ea5c3a1d341c8631b23664b077448417e04f5d5803938a6d3a868797`；Testcontainers 日志确认镜像 `redis:7.4.8` 与服务端版本 `7.4.8`。本次正式验收未使用 Redis 8.2.1 回退。

专项测试命令：

```powershell
mvn -s ../work-notes/maven-settings.xml '-Dtest=RedisReservationStoreTest,ReservationWarmupServiceTest' test
```

最终专项结果：19 项通过，0 failures/errors/skipped。包括 18 项真实 Redis 测试和 1 项预热编排单元测试。

| 场景 | 实际验证 |
| --- | --- |
| 1000 请求争抢库存 100 | 32 个工作线程；SUCCESS=100、SOLD_OUT=900、remaining=0，requests/pending 各 100 |
| 同一 requestId 重放 100 次 | reservationId、时间和 PENDING 记录保持相同，只扣一次库存 |
| 同用户不同 requestId 并发 | 仅一个 SUCCESS，另一个 DUPLICATE，只留一条预占 |
| 身份冲突 | 同 requestId 换 userId 返回 REQUEST_CONFLICT，不扣库存 |
| 活动与输入边界 | 未预热、开始前、结束后、售罄、活动隔离、大小写与超过 2^53 的用户 ID |
| 幂等预热与脚本缓存 | 再预热不覆盖已扣库存，SCRIPT FLUSH 后可继续执行 |
| 状态损坏 | 错误 key 类型、非规范数字、关联缺失、等基数孤立 pending 均被拒绝，不产生进一步写入 |
| 过期语义 | createdAt 来自 Redis TIME，expireAt=createdAt+120000；存在的 key 均无自动 TTL |

预占结果与库存断言来自 JUnit，不把 32 线程的 1000 请求描述为 1000 个同时在途请求，也不推导 QPS。

独立审查发现并修复了两项问题：查询原先未校验关联完整性；孤立 pending 在总数未变时可能被新请求覆盖。新增回归先失败再通过，两项修复均通过独立复核。首次全套测试运行在查询修复前，50 项中该新增回归失败；最终全套结果在下方单独记录。

Redis Compose 也已启动并通过健康检查；实测 `appendonly=yes`、`maxmemory-policy=noeviction`。测试使用临时空闲宿主机端口；本机 `16379` 属于其他项目，不占用或修改该服务。完成后停止并移除本次 Redis 容器，保留开发数据卷。

## 复现命令

项目根目录可执行 `mvn verify`，完整验证依赖目标 MySQL 和 Redis 镜像。本机 Maven 使用工作台的独立依赖缓存：

```powershell
mvn -s ../work-notes/maven-settings.xml verify
```

工作台之外可直接使用 `mvn verify`；POM 没有引用工作台私有绝对路径。

只验证阶段 2：

```powershell
mvn '-Dtest=RedisReservationStoreTest,ReservationWarmupServiceTest' test
```

启动依赖：

```powershell
docker compose --profile redis up -d --wait redis
docker compose up -d --wait mysql
```

若本机 3306 被占用，应同步设置 `FLASHGUARD_MYSQL_PORT` 和应用 `FLASHGUARD_DB_URL`，不能只改 Compose 端口。HTTP 基线的完整操作仍见 README。
